## D-001 P2를 원 코드 그대로가 아닌 Windows 환경 1개 경로로 실행

- **날짜:** 2026-10-15
- **사전 고정:** 6.3절 P2 "공개 체크포인트 3종으로 핵심 과제 4개를 평가 시드 3개로 평가", 3.2절 "P2는 원 코드를 고치지 않고 돌린다", 명령 예시 `train_ms3_ppo.py --only_render`(환경 64개, GPU 시뮬레이션).
- **실제:** Windows 네이티브에서 원 정책·래퍼 메서드를 그대로 가져다 쓰는 평가 루프([eval/p2_eval.py](eval/p2_eval.py))로 실행. 바꾼 것: CPU 시뮬레이션·환경 1개, CPU로 읽는 Vulkan 렌더링, EE 포즈 기구학 pinocchio(CPU 경로), sdpa attention(flash-attn 대신), 학습 데이터 모듈 대역, 초기 상태를 결정적 `episode_id`로 지정(체크포인트 간 공통). 생성 설정(온도 0.6, top_k 50)·성공 판정·에피소드 수는 원 코드와 같다.
- **사유:** WSL2에서 GPU Vulkan 렌더링 불가(P1-b), Windows에는 GPU 병렬 시뮬레이션이 없음. 원 코드의 초기 상태는 CUDA RNG에 의존해 정확히 재현할 수 없음. 6.0절이 Windows 네이티브를 대안으로 두었고, 연구자가 2026-10-15에 "ManiSkill 파일럿은 Windows 네이티브로" 결정.
- **결과를 보기 전/후:** 전.
- **영향:** 파일럿 한정. 본실험(Linux H200·H100)에는 해당 없음. P2 수치는 원 논문 조건과의 차이를 포함한다 ([P2_windows_eval_setup.md](P2_windows_eval_setup.md), [P2_results.md](P2_results.md)의 "원 논문과의 차이").
- **결정:** 연구자 (경로 선택), Claude (구현).

## D-002 P2 재현 판정: SFT 새 물체 0.4%p 초과를 "조건부 통과"로 재판정

- **날짜:** 2026-10-16
- **사전 고정:** 6.4절 재현 허용 범위 ±max(10%p, 원 논문 표준편차 × 2). SFT-16k 새 물체(Carrot test)는 45.3%, 허용 범위 35.3~55.3%. 6.5절 G1 "재현" 항목: 4과제 모두 범위 안이면 통과, 크기만 1~2과제 이탈이면 재검토. 6.3절 P2 실패 처리: "크기만 벗어나면 평가 조건(에피소드 수, 렌더러, 배치)을 대조한 뒤 재판정한다. 재판정은 1회까지만 한다."
- **실제:** 관측 55.7% (192 에피소드, SE 3.6%p), 상한을 0.4%p 초과 → 규칙상 "재검토". 평가 조건을 대조한 뒤 **조건부 통과**로 재판정한다. **재실행은 하지 않는다.**
- **재판정 근거 (평가 조건 대조):**
  1. 초과 폭 0.4%p는 이 추정치의 표준오차(3.6%p)의 약 0.1배, 원 논문 표준편차(4.4)의 약 0.1배다.
  2. 평가 조건이 원 논문과 다르다: CPU 시뮬레이션·환경 1개, pinocchio 기구학 경로, sdpa attention, 다른 고정 초기 상태 집합 (D-001).
  3. 이 과제는 초기 상태의 물체 구성에 민감하다. 시드 간 관측 SD 11.1%p로, 이항 잡음만의 SD(6.2%p)의 약 2배이고, 물체별 성공률 차이가 크다 (P2_results.md 세부 관찰 1).
  4. 같은 과제의 RL은 범위 안(69.3%)이고, 실행 축 2과제의 방향(RL > SFT)과 격차 크기(+44.8, +49.0%p)는 원 논문(+45.8, +45.9%p)과 거의 같다. 이 연구의 확증 분석 대상인 실행 축 재현에는 문제가 없다.
- **조건 (통과에 붙는 단서):**
  - SFT-16k의 새 물체 성공률은 이 환경에서 원 논문보다 높게 나온다(+10.4%p). 의미 축 결과를 원 논문 수치와 직접 비교할 때 이 차이를 함께 적는다.
  - 학습 조건의 RL−SFT 격차가 원 논문보다 훨씬 작다 (+1.6 대 +15.7%p). 1.2절의 "ID 대비 하락" 해석을 이 환경에 그대로 옮기지 않는다.
  - 이 판정은 파일럿 구현 확인(G1)에만 쓴다. 파일럿 수치는 논문 근거로 쓰지 않는다 (6.1절).
- **하지 않는 것:** 에피소드·시드를 추가해 범위 안으로 들이는 것, 허용 범위를 넓히는 것. 결과를 본 뒤의 재실행은 재판정 규칙의 취지(조건 대조)를 벗어나므로 하지 않는다.
- **결과를 보기 전/후:** **후** (P2 결과를 본 뒤의 재판정). 재판정 절차 자체는 6.3절에 사전에 정해져 있었고, 그 1회를 여기서 썼다.
- **영향:** G1의 "재현" 항목이 "통과(조건부)"가 된다. 다른 G1 항목(구현 검증 P4, 공급 측정 P3, 미니 실행 P5)은 아직 판정 전이다.
- **결정:** 연구자 (2026-10-16).

## D-003 P3를 배치 실행기(환경 3개 병렬, 배치 추론)와 0-B LoRA 병합 경로로 실행

- **날짜:** 2026-10-17
- **사전 고정:** 6.3절 P3 "W1 웜업으로 학습 과제 분포에서 1,024 에피소드를 온도 1.0, top_k = 0으로 수집 … 같은 초기 상태로 온도 0.6에서도 한 번 수집" (v0.9에서 top_k 50 수집 추가). 실행 경로는 정하지 않았으나, P2는 원 정책 경로(배치 1)였다.
- **실제:** 원 정책이 붙이는 0-B LoRA를 가중치에 병합(비트 단위 동일 확인)하고, CPU 시뮬레이션 환경 3개를 별도 프로세스로 돌려 같은 스텝의 관측을 배치 3으로 추론했다 ([speedup_and_batching.md](speedup_and_batching.md)). 초기 상태는 물체 16 × 테이블 16 × 4회 완전 교차를 `episode_id`로 직접 지정하고(위치·자세는 고정 시드 무작위), 세 설정(T1_K0, T1_K50, T06_K50)이 같은 1,024개 초기 상태를 쓴다.
- **사유:** 원 경로(에피소드당 30.7초)로는 P3(3,072 에피소드)가 약 26시간. 배치 실행기는 약 9초.
- **결과를 보기 전/후:** 전 (P3 실행 전에 결정·검증).
- **영향:** 배치 추론은 배치 1과 비트 단위로 같지 않다 (첫 토큰 분포 KL 약 0.0025). 같은 P2 초기 상태 64개에서 성공률은 구분되지 않았다 (P2 57/64, 배치 55/64, McNemar p = 0.75). P3 수치는 원래도 잠정치(G2에서 재측정, 3.7절)다.
- **결정:** Claude (연구자가 "속도 개선 후 진행 가능한 실험을 주도적으로 진행"하도록 위임, 2026-10-16).

## D-004 P5에서 KL 안정화 장치를 "기록만" 모드로 실행, 미니배치 2

- **날짜:** 2026-10-17
- **사전 고정:** 3.3절(v0.9) 우도 갈래의 라운드 안 KL 상한 조기 종료, KL_max 제안 0.05 (원 PPO의 라운드당 KL 분포를 G2에서 보고 G-PRE에 고정). 6.3절 P5는 장치 설정을 따로 정하지 않았다.
- **실제:** P5 두 시드 모두 KL_max를 사실상 무한대로 두고, 스텝마다 KL(라운드 시작 정책 대비 k3 추정, 성공 전이 고정 부분집합 32개)을 기록만 한다. 메모리 때문에 미니배치를 2로 나눠 스텝당 전이 160개를 누적한다(같은 평균).
- **사유:** 시험 실행에서 한 스텝 뒤 KL이 3.5로, 보정되지 않은 제안값 0.05의 70배였다 (AdamW 첫 스텝은 모든 파라미터를 약 lr만큼 움직인다). 0.05로 켜면 모든 라운드가 한 스텝 뒤 멈춰 P5가 학습 동작을 확인하지 못한다. KL_max는 원래 G2 측정으로 정하게 되어 있으므로, P5는 그 보정 자료를 모은다. 미니배치 4는 GPU 메모리를 넘겨(최대 23.3 GiB + 화면 출력) 스텝당 8분, 2는 19.0 GiB·0.5분.
- **결과를 보기 전/후:** 전 (P5 본 실행 전, 시험 실행의 메모리·KL 측정만 보고 결정).
- **영향:** 파일럿 한정. 본실험의 KL_max와 안정화 장치 적용은 G-PRE에서 정한다. KL 추정을 성공 전이로만 하므로 라운드 전체 배치 기준보다 크게 나올 수 있다.
- **결정:** Claude (위임 범위 안).

## D-005 P5를 수집·학습 분리 프로세스 구조로 실행하고 프로세스 실패를 자동 재시도

- **날짜:** 2026-10-17
- **사전 고정:** 6.3절 P5 "병합 W1 + 새 LoRA에서 출발해 A2⁺를 10라운드 돌린다 … 학습 시드 2개". 실행 구조는 정하지 않았다.
- **실제:** 라운드마다 수집과 학습을 별도 프로세스로 실행하고, LoRA 어댑터·optimizer 상태·성공 궤적을 디스크로 넘긴다 ([learner/p5_phased.py](learner/p5_phased.py)). 프로세스가 실패하면 같은 입력·시드로 다시 실행한다 (수집 2회, 학습 1회까지). 실제 실패: 학습 4회(시스템 RAM 부족, 업데이트 전), 수집 1회(0xC0000409). 모두 재시도로 성공했다. 상태는 학습이 끝난 뒤에만 저장하므로 실패한 시도가 상태에 흔적을 남기지 않는다.
- **사유:** 단일 프로세스 실행이 두 번 모두 라운드 1 수집 시작에서 충돌했다 (학습 뒤 환경 작업자 재생성 시점).
- **결과를 보기 전/후:** 전 (첫 두 실행은 라운드 0만 끝난 상태에서 중단, 그 결과는 쓰지 않음).
- **영향:** 학습 계산은 같다. 라운드 0 손실이 단일 프로세스 실행과 같았다(1.3057, 작은 시험). 수집을 다시 한 라운드는 같은 초기 상태·같은 샘플링 시드로 처음부터 수집했다.
- **결정:** Claude (위임 범위 안).

## D-006 G1을 "통과 (조건부)"로 확정

- **날짜:** 2026-10-19
- **사전 고정:** 6.5절 G1 판정표는 항목별로 "통과 / 재검토 / 중단"을 두고, 구현 검증은 "P4 시험 모두 통과"면 통과, "허용 오차를 넘는 시험 1~2개(원인 파악 후 재시험)"면 재검토다. "조건부 통과" 범주는 없다.
- **실제:** 1차 판정(2026-10-17)은 구현 검증 "재검토", 종합 "재검토"였다. 그 뒤 남은 항목을 모두 수행했다 (통제 PPO 학습기·E2 분기 코드, C10 반영 왕복 시험, 저장 모듈, 접촉 상태 복원). 실패했던 세 시험은 원인을 확인하고 통제 방법을 바꿔 다시 시험해 통과했다: C10(θ_old 재계산 → 첫 ratio 정확히 1), E2 분기 재현(결정적 GPU 설정 → 비트 단위 동일), 접촉 상태 복원(장면 재구성 + 전체 상태 복원 → 반복 비트 단위 동일). 연구자가 G1을 **통과 (조건부)**로 확정했다. 조건: (1) C10 적용 확정, C11(결정적 GPU 실행), E4-b 복원 절차를 명세에 반영 (명세 v0.11에서 반영), (2) 64 환경 전체 규모의 손실·기울기 확인을 G1 전 H200 제한 사용(5.1절 상한) 안에서 한다.
- **사유:** "재검토"의 정의(원인 파악 후 재시험)를 이행했고, 재시험이 바뀐 통제 방법으로 통과했다. 바뀐 통제 방법이 명세에 들어가야 통과가 의미를 가지므로 조건을 붙였다.
- **결과를 보기 전/후:** 후 (파일럿 결과를 본 뒤의 판정). 판정은 파일럿의 구현 확인에 관한 것이고 연구 가설의 결과와는 무관하다.
- **영향:** G2(H200 실측) 진입. 전체 규모 확인 결과가 나쁘면 G1을 다시 연다.
- **결정:** 연구자 (2026-10-19).
- **추가 기록 (2026-10-19, 6차 외부 검토 13번 반영):** 이 판정은 운영상의 조건부 승인이며 **G2 진입 승인**이다. 잔여 생성–학습 분포 불일치, Linux 전체 규모 동작, 복원 상태 타당성 검증이 끝나기 전까지 본실험 착수 승인을 뜻하지 않는다 (본실험 승인은 G-PRE). 위 "C10(θ_old 재계산 → 첫 ratio 정확히 1)"의 통과는 trainer 기준 ratio 정렬 시험의 통과이고, 생성–학습 분포 동일성 시험의 통과가 아니다 (명세 v0.12, 3.2절 C10).
- **D-002 관련 (같은 검토):** SFT 새 물체 +0.4%p 초과는 192회 평가의 에피소드 하나(약 0.52%p)보다 작아 파일럿 진입 판단에서 제한적으로 받아들였다. 원래 판정은 "재검토"였고, 범위 안에 드는 결과를 얻으려고 반복 실행하지 않았다.

## D-G2-1 S3 실행 순서를 판정 조건 우선으로 바꿈 (10 GPU시간 상한)

- **날짜:** 2026-11-03
- **사전 고정:** G2 명세 S3 — "RL·SFT 체크포인트 × 16조건 × 시드 0·1·2 → 웜업 × ID·실행 3조건 × 시드 0·1·2 → 웜업 나머지. 첫 체크포인트 하나의 실측 시간으로 전체를 외삽하고, 상한을 넘으면 웜업 나머지부터 뺀다." 상한 10 GPU시간.

## D-G2-4 S9 A2⁺ 비용 출력의 optimizer 스텝 수가 성공 수를 드러냄 (맹검 누출)

- **날짜:** 2026-11-05 (G2 결과 검토 중 발견, S9 종료 뒤)
- **사전 고정:** `docs/G2_prereg.md` 맹검 출력 — 화면·`cost_*.jsonl`에 라운드 시간·GPU 시간·피크 메모리·**optimizer 스텝 수**를 허용.
- **실제:** A2⁺(U-prop)의 라운드별 optimizer 스텝 수는 성공 에피소드 수의 함수다. 성공 에피소드 n개 × 80전이를 미니배치 8 × 누적 20 = 160전이 단위로 나누므로 스텝 수 = ⌈n/2⌉ (`g2_s9_train.py` `a2p_update`, `core.chunk_loss_divisors`; 라운드 1: 성공 35 → 18스텝). 따라서 `artifacts/g2/s9/cost_A2p.jsonl`·`log_A2p.txt`의 라운드별 `opt_steps`(그리고 이에 따라 움직이는 `update_s`·`round_s`)에서 A2⁺의 라운드별 성공 수를 ±1 안에서 되살릴 수 있다. 보고서 6절의 "스텝 10~22, 평균 15.7"도 평균 성공 수를 드러낸다. 이 파일들은 커밋 `4d529f3`로 공개 저장소에 올라갔다.
- **사전 고정 자체의 결함이다.** 실행은 사전 고정을 따랐다. U-prop에서 스텝 수와 업데이트 시간이 성공 수에 비례한다는 점을 맹검 출력 설계에서 놓쳤다.
- **결과를 보기 전/후:** 후. 누출된 값으로 A2⁺ 학습 곡선이나 성공률을 계산한 사람은 없다. Claude는 검토 중 라운드 1~4의 스텝 수(18·11·13·14)를 보았고 그 이상은 보지 않았다.
- **보충 (2026-11-06, H200 쪽 Claude):** G-PRE 예산표를 만들며 비용 합계를 확인하던 중 `log_A2p.txt`의 마지막 줄을 출력해 **라운드 50의 스텝 수(15)**를 보았다. 이후 A2⁺ 비용은 실행 전체 합계만 출력하는 스크립트(`pilot/g2/g2_gpre_budget.py`)로만 읽는다.
- **조치:**
  1. **δ는 사전 고정 규칙 그대로 기계적으로 정한다:** 측정 구간 평균 비율 0.576 → δ = 5%p. 경계 근처라는 점, 최대 라운드 시간 기준 비율(0.68) 등 누출 정보와 얽힌 재량 조정은 하지 않는다.
  2. 이미 공개된 파일은 지우지 않는다 (지워도 되돌릴 수 없고, 기록의 투명성을 유지한다). 이 기록 뒤로 누구도 이 값으로 A2⁺ 성능을 계산하지 않는다.
  3. **본실험(G-PRE) 맹검 출력:** A2⁺·성공 의존 비용 지표(스텝 수, 업데이트 시간, 라운드 시간)는 라운드별로 내지 않고 실행 전체 합계만 낸다. 라운드별 값은 `blinded/`에만 둔다.
  4. 보고서(`G2_results.md`) 맹검 문구에 이 누출을 적는다.
- **결정:** 연구자 기록 결정 (2026-11-05).
